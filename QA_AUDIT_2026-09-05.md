# ProcureNance live demo QA — 5 September 2026

Target: https://procurenance.roxas.workers.dev · Worker: `procurenance`.

## Release assessment

**An intermittent login failure remains a critical presentation risk on Workers Free.** A live login returned HTTP 503 and the matching Worker event reported `exceededCpu`. Earlier and later logins succeeded. The owner confirmed the account uses the Free plan. Do not interpret a successful single login as resolution. Keep bcrypt and MFA protections; move to an appropriate Worker CPU allowance and repeat authentication tests. No subscription or billing change was made.

This review combines source inspection, non-destructive live HTTP requests, sanitized Worker tail events, local security/model tests, frontend initial-render tests, lint, build, and deployment checks. Browser connection attempts returned no available browser. Real browser interaction, viewport rendering, authenticator confirmation and fully authenticated procurement workflows are **not verified** by these checks.

## Verified observations

- Baseline: six published project cards/details, all six timelines and document lists, branding/overview/filters, three announcements, announcement archive, 22 officials, public documents and legacy transparency API lists returned HTTP 200 with valid JSON.
- Public project document lists and public generated documents were empty. There were no public files available to use as live PDF/download fixtures.
- Nonexistent public project returned JSON 404; unmatched project search returned an empty array.
- Unauthenticated settings, notifications, users, contracts and invoices returned 401; hostile-Origin login was rejected with 403 before authentication.
- A later login returned a secure `__Host-` cookie with HttpOnly and SameSite=Lax. Three subsequent `/api/auth/me` requests returned 200; MFA state was readable; workspace APIs returned the intended 403 while unenrolled. Logging out returned 200, and reusing that script's old cookie returned 401.
- Hyperdrive API confirms `caching.disabled: true`; required named Worker bindings and secrets are present. Secret values were not printed.
- Worker tail captured one scheduled `*/30 * * * *` event with outcome `ok`, no logs and no exceptions. No COM_STMT_PREPARE, cross-request I/O, acquisition timeout or D1 failure appeared in that observed baseline. Later, a successful login and `/auth/me` each required the existing one-character JSON repair. The workaround is still necessary and was preserved. This is bounded observation, not historical log coverage or proof every detector rule ran successfully.
- 26 local QA/security tests pass (including route contracts for 17 configured roles), plus 17 TOTP algorithm checks. Initial server render of 41 screens passes; effects and browser layout are outside this check.
- Frontend lint/build and Wrangler dry-run pass. Both npm dependency audits report zero known vulnerabilities at time of review.
- Exact-value scan: two configured local secret values checked across 347 source/build files; no matching file; no tracked environment file found. Does not cover unknown remote secrets or history.
- The snapshot list and database-backed public controller (Express accepts a trailing slash, outside the Worker's exact snapshot match) both return six projects; checked titles, descriptions, categories, phases, references, financial figures and contract status agree.
- Live MFA enrollment after the first QA deployment returned HTTP 200 with a QR payload and expected parameters; the script logged out its own session. This replaces a pending enrollment, so the owner should start a fresh browser enrollment before scanning. No active enrollment was reset or confirmed, and no recovery code was consumed. A successful API payload does not establish browser rendering or authenticator confirmation.

## Still requires a controlled rehearsal

1. Resolve QA-01, then repeat the full browser MFA flow with each demonstrator's own authenticator. Keep QR/secrets/recovery codes out of recordings and shared screens. Do not reset existing enrollments just for testing.
2. Complete one normal authenticator sign-in and, on an authorized disposable account, one recovery-code sign-in; confirm that reuse fails and remaining-code status updates. Recovery testing consumes a code.
3. Exercise authenticated roles, permissions, forms, procurement transitions, approval/rejection, uploads, generated PDFs and financial workflows on a disposable staging dataset. Static route tests do not prove live database grants or workflow correctness.
4. Verify SMTP activation/password-recovery delivery to a test mailbox with explicit authorization. No test email or password reset was sent by this review.
5. Check mobile/narrow laptop layouts, keyboard-only navigation, browser console/network errors and theme rendering in actual browsers. The browser integration was unavailable here.
6. Snapshot data is a deployment-time copy. Aiven edits do not update snapshot endpoints automatically. Regenerate only from reviewed approved data and redeploy when the public presentation records change. Snapshot timelines/announcements/officials still use MySQL; it is not an offline copy of the entire site.
7. Existing security-audit release requirements still apply: audit durability/concurrency, database-backed financial race tests, backup/history cleanup and malware scanning are not certified by these smoke tests. Rotate the previously exposed database password before real/public use; do not change MFA encryption keys casually.
